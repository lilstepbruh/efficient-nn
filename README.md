# Homework 1 — аналитическая модель CNN

## Результаты

Выполнены реализация сети, аналитический вывод, измерения, калибровка и проверка предсказаний. Основная сетка: **132 точки**, из них 63 калибровочные и 69 исходных проверочных. Дополнительно собраны **2244 послойных времени**, полная серия совместного роста **S=512k, B=32k** до OOM и **16 новых контрольных точек**, выбранных до проверки окончательной модели.

| Модель / выборка | MAPE времени | MAPE энергии | MAPE памяти |
|---|---:|---:|---:|
| Исходный общий max, 69 проверочных | 12.08% | 16.14% | 38.72% |
| Окончательная послойная, 63 калибровочные | 6.23% | 18.55% | 42.05% |
| Окончательная, 69 исходных проверочных | 6.32% | 14.60% | 38.72% |
| **Окончательная, 16 новых контрольных** | **6.64%** | **12.81%** | **45.37%** |
| Совместное расширение, 6 успешных точек | 8.20% | 14.26% | 52.27% |

MAPE = среднее 100·|прогноз/измерение−1|. Память не калибруется: используем требуемую сумму активаций. Новые точки в основном относятся к средним/большим нагрузкам, поэтому их ошибку нельзя напрямую считать улучшением относительно другого состава исходной выборки.

## Среда и архитектура

GPU NVIDIA GeForce RTX 3090, класс 24 GB; driver 595.91.07. Python 3.11.15, PyTorch 2.13.0+cu130, CUDA runtime 13.0, cuDNN 92000, NumPy 2.3.5, SciPy 1.17.1, Matplotlib 3.11.1. NVML вызывается через ctypes. [Диагностика среды](results/environment.json).

[models.py](models.py) реализует исходную архитектуру задания без расширения каналов: 6 Conv с ReLU, MaxPool после первого блока, GlobalAvgPool, Linear512→256, ReLU, Linear256→100. Conv: padding=k//2, bias=False; Linear: bias=True. ReLU in-place, BatchNorm отсутствует, выход — логиты без Softmax. Всего **1 040 324 параметра**. [Проверка размеров 62 конфигураций](results/model_check.json).

Все основные измерения: FP32, eval(), inference_mode(), cudnn.benchmark=False, TF32 отключён для cuDNN и matmul. Более мощная GPU и расширение S/B разрешены уточнением преподавателя; основная сетка задания сохранена.

## Формулы и калибровка

Аналитические функции и послойные коэффициенты реализованы в [equations.py](equations.py).

- F = 17714·B·S² + 313700·B FLOPs; один MAC=2 FLOPs, сравнения ReLU/MaxPool исключены, bias Linear и GAP включены.
- M = 4·(1040324 + 26·B·S² + 868·B) байт: параметры, вход, сумма активаций без освобождения. In-place ReLU/Flatten не дублируются.
- D = 4·(1040324 + 91·B·S² + 2148·B) байт: идеализированное однократное чтение входа/параметров и запись выхода каждого оператора; не worst case.
- **T = Σᵢ max(τ, Fᵢ/C, Dᵢ/W)**, сумма по 17 операторам, без Flatten.
- **E = p₀·T + p₁·(T−17τ)**, джоули всего GPU. Idle не вычитается.

Коэффициенты Fᵢ,Dᵢ в [equations.py](equations.py) явны и зависят только от S,B; суммы совпадают с общими формулами. τ — эффективный минимум времени оператора, не утверждение об одном CUDA kernel на слой. Энергия допускает рост эффективной мощности от p₀ к p₀+p₁ при росте полезной нагрузки. [equations.py](equations.py) поддерживает числа и broadcasting NumPy. Старые параметры t0,q поддерживаются только для сравнения с архивным общим max.

W определяется независимо от общего времени: геометрическое среднее Dᵢ/tᵢ для **106 больших ReLU из калибровочных конфигураций**, логический трафик ≥64 MiB. Изолированные операции измерены CUDA Graphs и CUDA Events; повторное использование входов кэш-дружественно, эти времена не подменяют wall-clock latency сети. Затем τ,C подбираются по 63 временам всей сети, минимизируя средний квадрат log(T_pred/T_meas); 32 старта, seed 42. После фиксации времени p₀,p₁ подбираются по логарифмической ошибке энергии тех же 63 точек.

| Параметр | Значение |
|---|---:|
| τ | 18.7049 мкс/оператор |
| C | 14.9052 TFLOPs/с |
| W | 838.448 GB/с, десятичные байты |
| p₀ | 268.196 Вт |
| p₁ | 100.479 Вт |

Полные значения, источник W, SHA256 данных/кода, сходимость стартов: [theta.json](results/theta.json). Это эффективные коэффициенты модели, а не паспортные характеристики. 32 старта дали близкие τ,C; это численная устойчивость оптимизации, не доверительный интервал.

Исходные 69 точек не входят в fit, но их ошибки были просмотрены при развитии модели. Их результаты приведены как повторная проверка. Для окончательного подтверждения заранее объявлены новые 16 пропорциональных пар (S/B=16), измеренные после фиксации θ; параметры после их просмотра не менялись. [Протокол](results/fresh_confirmation/protocol.json), [контрольные метрики](results/supplemental_metrics.json).

## Обсуждение

**Зачем послойная модель.** У общего max величины F,D почти пропорциональны BS², поэтому скорость вычислений плохо определялась: близкие решения давали C от 11.5 до 174 TFLOPs/с. В новой модели разделены операции с разной интенсивностью, а W независимо закреплена измерениями ReLU. Ошибка времени на исходной проверке снизилась с 12.08% до 6.32%; на новой контрольной серии — 6.64%, максимальная 12.22%. Различия алгоритмов и размеров всё ещё вызывают ошибки на малых точках исходной сетки, максимум 52.57%. Выбор одной C и одного τ для всех операций — осознанное упрощение.

**Режимы.** Малые ReLU имеют почти постоянное время порядка 1.3 мкс; при увеличении тензоров оно растёт пропорционально трафику, а логическая полоса стабилизируется около 840 GB/с. Это согласуется с переходом от накладных расходов к ограничению передачей данных. Для Conv5 при S=512,B=32 измерено 18.13 TFLOPs/с при аналитической интенсивности 227 FLOPs/байт, тогда как ReLU1 на этой же точке достигает 844.69 GB/с. При калиброванных C/W≈17.78 FLOPs/байт модель относит большую Conv5 к вычислительной ветви, ReLU — к памяти. На 63 конфигурациях из 1071 пар «оператор/вход» модель назначает 584 накладным расходам, 259 вычислениям и 228 памяти. Это интерпретация послойной модели, поддержанная независимыми временами, а не прямое измерение загрузки SM/DRAM. Нельзя утверждать, что вся сеть обязательно последовательно проходит все три режима: они сосуществуют в разных слоях. Накладные расходы включают подготовку kernels и недостаточную загрузку, не только запуск CPU.

**Энергия.** Мощность зависит от нагрузки, поэтому E=qT заменена на p₀T+p₁(T−17τ). На новой контрольной серии MAPE=12.81%; на исходной проверке — 14.60%. Максимальная ошибка на исходных малых точках остаётся около 130%: единая пара коэффициентов не описывает весь диапазон мощности и алгоритмов. Значения p₀,p₁ эффективные, p₀ не является отдельным замером idle. NVML измеряет весь GPU и обновляется дискретно; три повторения снижают шум, но не дают гарантии абсолютной точности. Основная сетка измерена за одну сессию, влияние независимых сессий не оценено.

**Память и OOM.** Требуемая сумма активаций завышает большие реальные пики примерно на 50%, поскольку не моделирует освобождение. Для некоторых малых входов она занижает память: временные буферы и алгоритмы не учтены. На новой серии MAPE=45.37%; коэффициенты не подгонялись. При k=3.5 аналитическая сумма уже превышает объём карты, но реальный пик 22.79 GiB помещается; k=4 действительно вызывает OOM. Таким образом, формула описывает масштаб роста, но не точную границу. OOM — ограничение ёмкости, memory-bound — ограничение скорости; они не эквивалентны.

Выводы о режимах основаны на модели и измеренных временах; прямое подтверждение аппаратными счётчиками SM/DRAM не выполнялось.

## Воспроизведение

Команды выполняются из корня проекта в Python-окружении с указанными выше библиотеками. Повтор калибровки по сохранённым основным и послойным данным:

```bash
python hw1/calibrate.py
```

Команда перезаписывает theta.json, metrics.json и predictions.csv. Для сохранения исходной фиксации параметров сначала скопировать каталог results и передать копию через --results PATH. Сохранённые дополнительные предсказания относятся к исходному theta.json; их контрольная сумма записана в supplemental_metrics.json.

Новый прогон основной сетки на GPU в отдельный каталог:

```bash
python hw1/measure.py --output-dir hw1/results/repeat_run
```

measure.py не перезаписывает существующие измерения; --resume требует совпадения протокола, исходников и среды. OOM записывается в CSV без значений времени и энергии. Послойные, дополнительные измерения и готовые графики сохранены в results; эти серии не запускаются указанной командой основной сетки.

SHA256 исходников в протоколах и theta.json идентифицируют экспериментальную версию кода и могут отличаться от текущей версии с теми же формулами. Контрольные суммы данных относятся к сохранённым измерениям.
