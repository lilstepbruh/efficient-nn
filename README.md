# Homework 1 — аналитическая модель CNN

## Модель и среда

CNN из задания: 6 свёрток с ReLU, MaxPool после первой, GlobalAvgPool и два линейных слоя 512→256→100 с ReLU между ними. Conv без bias, Linear с bias; ReLU in-place, BatchNorm отсутствует. Всего **1 040 324 параметра**. Архитектура — [models.py](models.py), аналитические функции с broadcasting NumPy — [equations.py](equations.py).

GPU: **NVIDIA RTX 3090, 24 GB**, драйвер 595.91.07. Python 3.11.15, PyTorch 2.13.0+cu130, CUDA 13.0, cuDNN 92000, NumPy 2.3.5, SciPy 1.17.1, Matplotlib 3.11.1. Измерения: FP32, `eval()`, `inference_mode()`, `cudnn.benchmark=False`, TF32 отключён.

## Формулы и калибровка

Для размера изображения S, кратного 16, и батча B:

- **F = 17714·BS² + 313700·B** FLOPs. MAC = 2 FLOPs; сравнения ReLU/MaxPool исключены, bias Linear и усреднение включены.
- **M = 4·(1040324 + 26·BS² + 868·B)** байт. Параметры, вход и сумма активаций без освобождения; ReLU in-place и Flatten не дублируют хранение.
- **D = 4·(1040324 + 91·BS² + 2148·B)** байт. Один проход чтения входа/параметров и записи выхода каждого оператора; идеальное переиспользование внутри оператора, без переиспользования между ними.
- **T = Σᵢ max(τ, Fᵢ/C, Dᵢ/W)** секунд, сумма по 17 операторам без Flatten.
- **E = p₀T + p₁(T−17τ)** джоулей всего GPU, без вычитания idle.

τ — эффективный минимум времени оператора, C — вычислительная производительность, W — пропускная способность. W оценена по 106 большим калибровочным ReLU с трафиком ≥64 MiB: геометрическое среднее Dᵢ/tᵢ. Изолированные времена измерены CUDA Events с CUDA Graphs. Далее τ,C подбирались по времени сети, p₀,p₁ — по энергии при фиксированной модели времени. Целевая функция — средний квадрат логарифма отношения прогноза к измерению.

[Параметры](results/theta.json): **τ=18.7049 мкс, C=14.9052 TFLOPs/с, W=838.448 GB/с, p₀=268.196 Вт, p₁=100.479 Вт**. Это эффективные коэффициенты, а не паспортные характеристики GPU.

## Измерения и результаты

Основная сетка — 132 конфигурации: 63 базовые для калибровки, 69 дополнительных для проверки. Seed 42; случайные S=[80,272,352,400], B=[29,56,179]. На точку: 10 прогревов, медиана 21 wall-clock замера с CUDA synchronize, отдельный `max_memory_allocated()` и медиана трёх NVML-интервалов энергии длительностью ≥1 с. Вход уже на GPU; предыдущий выход не удерживается при измерении памяти. Энергия интервала делится на число проходов. [Данные](results/measurements.csv), [протокол](results/measurement_protocol.json).

Ошибки исходных 69 проверочных точек рассматривались при выборе модели. Поэтому дополнительно проверены **16 новых конфигураций**, объявленных заранее и измеренных после фиксации θ. Они не участвовали в подборе параметров.

|---|---:|---:|---:|
| Исходные 69 проверочных | 6.32% | 14.60% | 38.72% |

Для поиска OOM одновременно увеличивались **S=512k, B=32k**, k=1, 1.5, …, 4. При k=3.5 (S=1792, B=112) пик составил **22.79 GiB**; при k=4 (S=2048, B=128) получен **OOM**. Каждая конфигурация запускалась в отдельном процессе; для OOM время и энергия отсутствуют. [Данные расширения](results/joint_performance/measurements.csv).

## Обсуждение

**Время и режимы.** Послойная модель разделяет операции с разной арифметической интенсивностью. Малые ReLU выполняются примерно за 1.3 мкс; при росте тензора время становится пропорционально трафику, а эффективная полоса стабилизируется около 840 GB/с. Это согласуется с переходом от накладных расходов к ограничению памятью. Для Conv5 при S=512,B=32 измерено 18.13 TFLOPs/с при расчётной интенсивности 227 FLOPs/байт. Порог C/W≈17.78 FLOPs/байт относит эту свёртку к вычислительной ветви модели, а ReLU — к памяти.

Режимы сосуществуют в разных слоях: вся сеть не обязана последовательно проходить launch-bound → memory-bound → compute-bound. τ включает накладные расходы и неполную загрузку GPU, а не только запуск ядра. D — идеализированный трафик, не измеренные обращения к DRAM; повторные изолированные операции могут использовать кэш. Прямого подтверждения аппаратными счётчиками SM/DRAM нет. Единые C, W и τ не отражают все алгоритмы и размеры: максимальная ошибка времени на исходной проверке — 52.57%, на новых точках — 12.22%.

**Энергия.** Средняя мощность модели растёт от p₀ к p₀+p₁ с увеличением нагрузки; p₀ не является измеренной мощностью простоя. На малых исходных точках ошибка энергии достигает примерно 130%: одна пара коэффициентов не описывает весь диапазон мощности. NVML измеряет весь GPU и обновляется дискретно; длинные интервалы и повторы уменьшают шум. Влияние независимых сессий на основные результаты не оценивалось.

**Память.** Сумма активаций завышает большие реальные пики примерно на 50%, поскольку не учитывает освобождение. Для некоторых малых входов оценка занижена из-за исключённых временных буферов и округлений. При k=3.5 аналитическая сумма уже превышает ёмкость карты, хотя измеренный пик помещается. Формула отражает рост пространственной составляющей как k³, но не точную границу OOM. OOM означает нехватку ёмкости; memory-bound означает ограничение скорости передачи данных.

## Воспроизведение

Из корня проекта, в Python-окружении с указанными библиотеками:

```bash
# Калибровка по сохранённым данным в отдельной копии результатов
cp -r hw1/results /tmp/efficient_nn_hw1_recalibration
python hw1/calibrate.py --results /tmp/efficient_nn_hw1_recalibration

# Новый прогон основной сетки на GPU
python hw1/measure.py --output-dir hw1/results/repeat_run
```

`calibrate.py` использует основные и послойные CSV и записывает θ, метрики и предсказания. `measure.py` обрабатывает OOM и не перезаписывает существующие измерения; `--resume` требует совпадения протокола. Дополнительные серии и графики сохранены готовыми; команда основной сетки их не пересоздаёт.

SHA256 исходников в протоколах относятся к экспериментальной версии до объединения модулей; формулы и сохранённые параметры не изменялись. Контрольная сумма θ для дополнительных предсказаний находится в `supplemental_metrics.json`.
